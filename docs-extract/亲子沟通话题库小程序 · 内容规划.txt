# 亲子沟通话题库小程序 · 内容规划与生产手册
版本：v2.0　日期：2026-08-07
本手册是内容生产者的唯一参考文档，自包含全部必要信息，无需查阅其他技术文档即可完成内容扩容、训练计划配置、专题包生产等全部工作。v2.0 相较 v1.0 新增了"产品架构与内容全景"章节（第一章），让内容生产者理解内容如何在产品中被消费、各内容块之间的依赖关系、以及推荐的生产顺序；在中篇训练计划章节补充了跨内容块联动的操作流程——当训练计划需要一个尚不存在的话题时，必须先去话题库扩容中生产该话题、拿到其 `_id`，再回来填写训练计划的 `topicId`；在话题库扩容章节补充了 `_id` 续编规则和生产联动说明。
本手册整合了原 `内容优化方案.md` 和 `内容生成规划文档.md` 的全部内容，并补充了原两份文档缺失的话题包生产方案、内容写作规范、运营节奏、版本管理等内容。分为三篇：上篇"内容规划"定义做什么内容（含产品架构全景和各内容块的依赖关系），中篇"内容生成"定义每块内容怎么写（含跨内容块联动的操作流程），下篇"内容导入"定义生成后怎么导入数据库。所有内容块统一通过 `importData` 通用导入工具导入，不再区分"控制台手动录入"和"云函数导入"。

# 上篇 · 内容规划
## 一、产品架构与内容全景
本章节帮助内容生产者理解：小程序有哪些内容线、内容在产品中如何被用户消费、各内容块之间存在什么依赖关系、以及推荐的生产顺序。理解这些，才能在做某一内容块时知道它在全局中的位置、会受到哪些前置约束、以及缺失某个依赖时该怎么处理。
### 1.1 三条内容线
小程序的内容分为三条独立的线，它们共存于首页，面向用户的不同需求：
**A 线：话题库（communication_topics 集合）**——小程序的基础内容底座。300 条已有话题 + 后续扩容的新话题，每条是一个独立场景的话术指南（3 个错误示范 + 3 个正确示范 + 专家贴士）。用户通过「话题库」页面按年龄段和分类浏览搜索，或通过首页「今日推荐」每天看到 3 条。话题库中的部分话题标记为付费（`isFree: false`），需要购买会员（59 元）或购买包含该话题的专题包（9.9 元）才能查看详细话术。话题库是全部内容的基础——B 线的训练计划直接引用话题库中的 `_id` 作为每日学习内容，C 线的话题关联关系也以话题库中的 `_id` 为索引。
**B 线：体系化引导（training_plans + topic_relations 集合）**——结构化的按天学习路径。包含入门计划（3 套，每套 7 天，免费）和主题周（首批 7 个，每个 7 天，均需会员解锁）。用户从首页的「训练卡片」入口进入，每天打开一条话题学习，系统记录进度。入门计划走「7 天入门→主题周推荐」的递进路径。这条线的内容本身不是独立的话题，而是对话题库已有话题的编排和引导文案包装——每条训练计划的 `days[].topicId` 指向话题库中的一条具体话题。话题关联关系（`topic_relations`）则定义了"学完这条话题后推荐哪几条相关话题"，用于话题详情页的场景推荐模块。
**C 线：专题包（communication_packages 集合）**——按主题深度展开的付费系统课程。每个专题包围绕一个育儿主题（如"情绪火山""作业拖延症"），包含 20-30 章图文内容，每章 2-4 个小节，章节按「部分」分组（认知篇/场景篇/关系篇/进阶篇/工具篇）。**专题包不再独立于话题库**——每个包同时打包该主题的实战话题（通过 `partTopics` 字段关联），买一个包即解锁其章节正文与对应话题。用户从首页「沟通专题」横滑区域进入。专题包采用双 SKU 模型：单独购买 9.9 元/包，或购买会员 59 元全解锁 11 个包。全部 11 个包均支持单买。`payService` 的 `VALID_PACKAGE_IDS` 通过 `packageData` 的 `validIds` action 动态获取，不再硬编码。
### 1.2 首页五状态与用户流转
首页训练卡片区域根据用户的训练状态展示 5 种不同形态，内容生产者需要理解每种状态对应的内容消费方式：
状态 1「未开始」（`not_started`）：用户首次打开小程序或未点击"开始入门"。训练卡片展示入门计划介绍和"开始入门"按钮。用户点击后进入入门计划 Day 1 的话题详情页。此时消费的是 B 线入门计划的 Day 1 内容（`topicId` 指向的话题 + `guide` 引导文案）。
状态 2「进行中」（`in_progress`）：用户正在 7 天入门计划中（Day 1-7）。训练卡片展示"第 N 天 · 今日主题"摘要和"继续学习"按钮。用户点击进入当天话题详情页，学习后点击"完成今日学习"，进度推进到下一天。此状态消费的是入门计划中对应 day 的内容。
状态 3「入门完成」（`onboarding_done`）：用户完成 7 天入门计划，尚未选择主题周。训练卡片展示"入门完成"庆祝信息和推荐的主题周列表。用户选择一个主题周后进入状态 4。此状态消费的是 B 线主题周的计划列表数据。
状态 4「主题周进行中」（`theme_week_active`）：用户正在某个主题周中（Day 1-5/6）。训练卡片展示当前主题周名称、第 N 天/总天数、今日主题摘要。消费方式同状态 2，但内容来源是主题周计划而非入门计划。
状态 5「主题周完成」（`theme_week_done`）：用户完成当前主题周。训练卡片展示"本周完成"庆祝信息 + 推荐下一个主题周或引导浏览话题库。用户可以选择新的主题周（回到状态 4）或去话题库自由探索。
### 1.3 页面与内容的对应关系
内容生产者需要知道生产的内容最终在哪个页面展示，以下是关键页面与内容线的对应关系：
首页（`pages/index`）：4 个区域。Hero 区（静态 banner，无内容生产需求）；训练卡片区（展示 B 线入门计划/主题周，5 种状态对应 5 种形态）；PDF 专题入口区（展示 C 线专题包封面和入口，对应 `communication_packages`）；今日推荐区（展示 A 线话题库中的 3 条每日推荐话题，由 `topicData` 云函数的 `dailyRecommendations` 接口随机选取）。
话题详情页（`pages/topic-detail`）：展示 A 线话题库中单条话题的完整内容（场景描述、错误示范、正确示范、贴士）。页面底部有"场景推荐"模块，展示来自 C 线 `topic_relations` 的关联话题（最多 3 条）。如果该话题是从训练计划跳转来的（URL 带 `from=plan` 参数），页面顶部会额外展示当天的引导文案 `guide` 和学习标签 `label`。
话题库页面（`pages/topic-library`）：展示 A 线话题库全部话题，支持按年龄段切换（3-6/7-9/10-12）、按一级分类筛选、关键词搜索。入门计划完成后引导用户来此自由探索。
开发者导入页面（`pages/developer-import`）：内容导入入口，通过 `importData` 云函数将生产好的 JSON 数据导入云数据库。详见下篇。
### 1.4 内容块依赖关系
各内容块之间存在依赖关系，生产时必须遵循先后顺序。以下是完整的依赖关系表：
| 内容块 | 存储集合 | 依赖谁 | 依赖说明 |
|---|---|---|---|
| F. 话题库扩容 | `communication_topics` | 无 | 基础内容，无前置依赖。`_id` 在各年龄段现有 100 条之后续编 |
| A. 入门计划配置 | `training_plans` | F（话题库） | 每个 `days[].topicId` 必须在 `communication_topics` 中存在。当前 21 个 topicId 全部来自现有 300 条，无扩容依赖；后续如改用新增话题，需先完成 F 的对应条目 |
| B. 主题周配置 | `training_plans` | F（话题库） | 同 A，每个 `days[].topicId` 必须在 `communication_topics` 中存在 |
| D. guide 引导文案 | 嵌入 A/B 的 days 数组 | A 或 B | 不是独立内容块，随 A/B 一起生产，但需在 A/B 的 topicId 确定后才能针对话题内容写引导文案 |
| C. 话题关联关系 | `topic_relations` | F（话题库） | `topicId` 和 `related[].topicId` 都必须在 `communication_topics` 中存在 |
| E. 专题包内容 | `communication_packages` | 无 | 独立内容线，不依赖话题库。但 `payService` 的 `VALID_PACKAGE_IDS` 需包含专题包 `_id` |
依赖关系图（箭头表示"依赖于"）：
```
F. 话题库扩容 ←── A. 入门计划（topicId 依赖）
                ←── B. 主题周（topicId 依赖）
                ←── C. 话题关联关系（topicId 依赖）
D. 引导文案 ──→ 嵌入 A/B（随 A/B 一起生产，不可独立）
E. 专题包（独立，无依赖）
```
### 1.5 推荐生产顺序
基于依赖关系，推荐的生产顺序如下：
第一批（阶段一并行）：F（话题库扩容首批，7-9 岁 15 条）+ A（3 套入门计划配置 + D 引导文案）。入门计划当前全部从现有 300 条选题，不依赖扩容，可并行。但如果你在设计入门计划时发现某个理想场景在现有话题库中不存在，需要先在 F 中生产该话题、拿到 `_id`，再回到 A 填写 `topicId`——这就是跨内容块联动，详见第 1.6 节。
第二批（阶段二）：B（7-9 岁主题周 + D 引导文案）+ E（专题包首批 3 个）。主题周同样可能遇到"理想场景不在现有话题库中"的情况，处理方式同上。
第三批（阶段二补充 + 阶段三）：B（3-6/10-12 岁主题周）+ C（话题关联关系）+ E（专题包第二批）。关联关系必须在话题库稳定后生产，否则话题 `_id` 可能变动导致关联失效。
### 1.6 跨内容块联动：训练计划选题时的话题补产
这是内容生产中最关键的流程之一。当你在编写训练计划（入门计划或主题周）的选题清单时，可能发现某个理想的场景在现有 300 条话题库中不存在。此时不能跳过或用近似话题凑数，必须执行以下流程：
第一步：在选题清单中标记该 day 的 `topicId` 为"待补产"，记录你需要的场景描述和年龄段。
第二步：切换到 F（话题库扩容）工作流，按上篇第三章的子场景清单和第五章的写作规范，生产这条新话题。它将获得一个续编的 `_id`（如 `ph_7_9_101`、`ph_3_6_101`、`ph_10_12_101` 等，详见第十三章的 `_id` 续编规则）。
第三步：回到训练计划选题清单，用新话题的 `_id` 填写该 day 的 `topicId`，并根据新话题的实际内容（`scenario`、`scenarioDesc`、`wrongScripts`、`rightScripts`）编写对应的 `guide` 引导文案。
第四步：在内容校验清单（第十七章）中逐项检查 `topicId` 是否在 `communication_topics` 中确实存在。
这就是为什么本手册将话题库扩容和训练计划配置放在同一份文档中——它们的生产是交织的，不是完全串行的。入门计划和主题周的选题会驱动话题库扩容的需求，话题库扩容的新增话题又会反哺训练计划的选题空间。
## 二、内容现状评估
现有 300 条话题内容质量扎实、结构统一，三个年龄段（3-6/7-9/10-12 岁）各 100 条。字段结构为 `scenario`（场景标题）/`scenarioDesc`（场景详细描述）/`level1`+`level2`（一二级分类）/`wrongScripts`（3 个错误示范+分析）/`rightScripts`（3 个正确示范+分析）/`tips`（专家贴士）/`tags`（3 个标签）。
现有一级分类覆盖情况：
3-6 岁 10 个分类，每类 10 条：饮食与进餐、睡眠与作息管理、情绪爆发与行为控制、社交互动与分享意识、习惯养成与自理能力、屏幕与电子产品管理、分离焦虑与幼儿园适应、认知与学习启蒙、安全规则与底线意识、亲子沟通与二胎家庭关系。
7-9 岁 7 个分类，条数 10-20 不等：学习与作业管理（20）、生活习惯与健康管理（15）、电子产品与网络行为（15）、社交互动与同伴关系（15）、规则意识、金钱观与社会化发展（15）、情绪管理与心理支持（10）、独立生活与自理能力（10）。
10-12 岁 7 个分类，条数 15-20 不等：学业与作业管理（20）、电子产品与娱乐管理（15）、生活作息与习惯养成（15）、情绪管理与青春期前奏（15）、社交与同伴关系（15）、消费与金钱观、兴趣发展与家庭态度（15）。
三个年龄段的一级分类几乎全部集中在"问题行为应对"——孩子已经出现问题行为，家长需要一套应对话术。这在实用性上没问题，但会让小程序给人的整体印象是"专治熊孩子的说明书"，而不是"帮你和孩子建立更好关系的工具"。
## 三、内容扩容方向
建议扩充两个新方向，与现有结构完全兼容（复用现有字段结构，无需改动数据模型）：
**主动关系建设类**：不是等孩子出问题才用的话术，而是家长主动发起、日常就能用上的沟通场景，比如每天接送时怎么聊天、怎么陪孩子读绘本、怎么在孩子分享心事时接住话头。这类内容目前是空白，但恰恰是"预防问题"而不是"处理问题"的场景，长期看更能建立用户粘性和日常打开频次。每个年龄段新增 15-20 条，共 45-60 条。新增一级分类：3-6 岁"日常沟通与情感连接"、7-9 岁"主动沟通与亲子陪伴"、10-12 岁"深度沟通与信任建立"。
子场景清单（3-6 岁 15 条）：接送路上/睡前的"今天开心吗"式闲聊怎么问；陪孩子读绘本时怎么提问引导表达；孩子主动分享一件事时怎么回应鼓励；孩子说"我喜欢你"时怎么回应强化安全感；孩子做对小事时怎么夸奖比"你真棒"更有效；家长自己情绪不好时怎么跟孩子解释；怎么和孩子聊"今天最高兴/最不高兴的事"；孩子提"为什么"式好奇提问怎么回应；二胎家庭怎么和大宝聊"你不是不被爱了"；怎么和孩子聊死亡/离别；怎么和孩子一起制定家庭小规则；孩子想帮忙做家务越帮越乱怎么回应；怎么聊身体隐私和安全边界；睡前怎么聊"明天想做什么"建立期待感；怎么回应孩子的"胡编乱造"想象力。
子场景清单（7-9 岁 15-20 条）：接孩子放学怎么问比"今天在学校怎么样"更能打开话匣子；孩子主动吐槽同学/老师时怎么回应；怎么和孩子一起做事时自然聊开话题；孩子考砸了没说怎么主动开口；怎么和孩子聊TA喜欢的动画/游戏建立共同语言；孩子第一次经历失败时怎么陪伴；怎么聊"什么是好朋友"；孩子分享秘密时怎么回应；怎么用提问代替说教；父母吵架后怎么和孩子解释；怎么和孩子复盘一天/一周；孩子对某兴趣有天赋时怎么鼓励不功利；怎么聊"什么谎话不能说"；怎么一起看新闻/时事；怎么用"共情式提问"代替"你怎么又"式指责。
子场景清单（10-12 岁 15-20 条）：青春期前奏有小秘密怎么保持沟通；怎么和孩子聊TA喜欢的异性/暗恋不尴尬；孩子第一次顶嘴怎么回应；怎么聊身材/外貌焦虑；怎么讨论"未来想做什么"不预设立场；孩子质疑家长决定怎么回应；怎么聊网络上看到的争议内容；怎么一起制定"家庭协议"；成绩下滑不愿谈怎么打开话题；怎么聊友谊中的排挤；怎么谈"失败是成长的一部分"；孩子有自己审美和家意见不合怎么沟通；怎么聊网络交友边界；孩子情绪低落不愿说怎么留空间；怎么聊"我们家和别人家不一样"的敏感话题。
**时效性/节日类**：和具体时间节点绑定的话题，比如开学前的分离焦虑、寒暑假作息重建、春节压岁钱怎么管。这类内容适合配合首页"今日推荐"在对应时间点集中曝光，带来季节性流量。每个年龄段 8-10 条，共 24-30 条，大部分场景框架可跨年龄段复用，按年龄段调整话术难度。
子场景清单（全年龄段共 10 个场景框架）：开学前一周的分离焦虑/新学期焦虑；暑假最后一周赶作业的拖延症和亲子冲突；寒暑假作息重建；春节压岁钱怎么管；春节走亲戚被过度盘问成绩/身高时怎么帮孩子应对；中秋/春节家庭团聚怎么聊家风增强归属感；儿童节/生日怎么聊"想要的"和"需要的"的区别；六一/寒暑假的"愿望清单"沟通；考试季考前焦虑疏导和考后成绩沟通；转学/搬家等重大生活变化的适应性沟通。
## 四、专题包设计
### 4.1 定位
专题包是独立于体系化引导（入门计划+主题周）的另一条内容线。体系化引导是"免费的、按天推进的结构化学习路径"，专题包是"付费的、按主题深度展开的系统课程"。两者共存但定位不同：体系化引导负责拉新和日活（免费引流），专题包负责变现（9.9 元/包或 59 元会员全解锁）。
原有 3 个专题包以 PDF 形式提供（睡前聊天、家园沟通、家校通信），现已升级为 11 个章节化专题包，对应 `communication_packages` 集合，ID 分别为：emotion、homework、habit、screen、social、money、routine、separation、safety、interest、connection。`payService` 中的 `VALID_PACKAGE_IDS` 通过 `packageData` 的 `validIds` action 动态获取，不再硬编码。单价 9.9 元/包，11 个包全部支持单买，会员 59 元自动解锁全部。
规划 11 个章节化专题包，按"高频痛点场景"而非"年龄段"划分主题（包内再按年龄段区分内容深度）。**主题划分不是拍脑袋，而是从话题库真实的 24 个 `level1` 归并而来，保证 300 道话题 100% 被覆盖。** 内容形式为章节化图文（`communication_packages` 集合 + 小程序内翻页阅读页），每个包拥有独立的渐变色封面（`gradientFrom`/`gradientTo`），并通过 `partTopics` 关联该主题的实战话题。后续按季度扩充新包。

### 4.4 专题包与现有付费体系的关系
`payService` 云函数通过 `packageData` 的 `validIds` action 动态获取 `VALID_PACKAGE_IDS`（带 5 分钟缓存 + 兜底列表），不再硬编码。新增专题包只需：
1. 往 `communication_packages.json` 追加文档（含 `gradientFrom`/`gradientTo`/`parts`/`partTopics` 等字段）
2. 通过 `importData` 导入到云数据库
3. 重新部署 `importData` 云函数（如尚未部署）
4. `payService` 会在 5 分钟缓存过期后自动识别新包 ID
`purchaseType` 字段已废除，11 个包全部支持单买。前端列表页和详情页统一显示 `¥9.90 解锁` 价格按钮。

## 五、内容写作规范
现有 300 条话题的写作风格没有文档记录，新内容如果由不同的人写，风格会不一致。以下规范从现有高质量话题中提炼，作为新内容的生产标准。
### 5.1 scenario（场景标题）
15-30 字，一句话描述一个具体的、可识别的场景。不是抽象的概念词，而是"什么人在什么情况下遇到了什么问题"。用家长的第一视角描述，不出现"家长应该""建议"等指导性词汇。
好的示例："面对特定的蔬菜或没见过的食物坚决不吃，甚至哭闹抗拒"
不好的示例："关于挑食问题的沟通策略"（太抽象，看不出具体场景）
### 5.2 scenarioDesc（场景详细描述）
50-120 字，把场景展开成一段具体的生活画面。描述孩子具体说了什么、做了什么、家长面临的即时困境是什么。以"作为家长，你会怎么回应"结尾，引导用户思考。
### 5.3 wrongScripts（错误示范）
3 条，每条包含 `title`（10 字以内的类型标签，如"威逼利诱型""情感绑架型""贴标签与比较型"）、`content`（家长实际会说的话，用引号引出，30 字以内）、`analysis`（为什么这种说法无效甚至有害，50-100 字）。
`analysis` 的写法：先指出这句话传递了什么错误信号，再说孩子会因此产生什么心理反应，最后点明长期后果。不用学术术语，用"这会让……""孩子会因此……"的日常语言。
### 5.4 rightScripts（正确示范）
3 条，结构同 wrongScripts。`title` 用积极的方法标签（如"接纳情绪，解除压力""提供有限自主权""大人示范，引发好奇"）。`content` 是家长可以实际说出口的话。`analysis` 解释为什么这种说法有效，孩子的心理感受会发生什么变化。
### 5.5 tips（专家贴士）
80-150 字，一段话。不是复述前面的内容，而是从更高的视角总结这个场景的本质问题，给出一个核心理念。语气像有经验的朋友在给你建议，不是教科书。避免"你应该""你必须"，用"记住""关键是""其实"等引导词。
好的示例："孩子对新食物的抗拒，是其发展感官边界和自我意识的必经阶段。在餐桌上，家长的角色不是负责分配定量的'监工'，而是探索食物的'向导'——先接纳情绪卸下防备，再通过互动引导接触，最后把'吃不吃'的决定权交还给孩子。记住：餐桌的氛围永远大于吃进去的食物。"
### 5.6 tags（标签）
3 个，口语化关键词。既包含专业的分类词（如"挑食""拒食"），也包含家长可能搜索的大白话（如"不吃饭""不爱吃菜"）。目的是让用户用各种自然语言都能搜到这条话题。
### 5.7 guide（引导文案，仅体系化引导用）
30-50 字，写法见中篇第五章。不复述 scenario，用对话感引导用户进入今天的话题。
### 5.8 整体语气基调
温暖但不煽情，专业但不学术，实用但不机械。像一个懂儿童心理的好朋友在跟你聊天，不像一个居高临下的专家在训话。避免"绝对""一定""必须"等绝对化表述。
## 六、运营节奏
### 6.1 每日推荐
现有 `topicData` 的 `dailyRecommendations` action 按 `hash(dateKey + ageGroup) % total` 从 `communication_topics` 中取 3 条。前端按当天日期缓存（key 为 `daily_reco_{dateKey}`）。话题库扩容后，每日推荐的候选池自动扩大，不需要改算法。
### 6.2 更新频率
话题库：不定期更新，每次新增 10-15 条为一个批次，通过 `importData` 导入。导入后在话题库页面自动可见（如果是新 `level1` 分类，需 `level1List` action 上线后才在分类标签栏显示）。
主题周：按月更新，每月新增 1-2 个主题周。新主题周上线时在首页训练卡片无需特别操作——用户完成当前计划后会自然在 `theme-week-list` 页面看到新选项。
专题包：按季度更新，每季度新增 1-2 个专题包。新专题包上线需要同步扩展 `payService` 的 `VALID_PACKAGE_IDS` 和 `pdf-files.js`（或 `communication_packages` 集合）。
节日/时效性话题：提前 2 周准备，提前 1 周导入。在对应的节日/时间节点前 3 天通过每日推荐集中曝光（调整 `dailyRecommendations` 的取数逻辑或手动指定推荐话题）。
### 6.3 内容版本管理
`importData` 的 upsert 语义（`doc(_id).set()`）保证了相同 `_id` 的记录会被覆盖更新。内容迭代时直接修改 JSON 文件、重新部署、重新导入即可。
灰度新内容的做法：新话题先用 `isFree: true`（免费）导入，在话题库中自然展示，观察用户收藏和反馈数据。如果数据好，可以纳入后续主题周编排或专题包内容；如果数据差，可以修改 `status` 为 `"draft"` 从列表中隐藏（`topicData` 的查询条件包含 `status: "published"`）。

### 8.5 跨内容块联动：选题时发现理想场景不存在怎么办
入门计划当前 21 个 topicId 全部选自现有 300 条话题，无需扩容。但后续迭代中，你可能会发现某个理想的入门场景在现有话题库中不存在。例如：你想为 3-6 岁入门计划 Day 5 选一条"孩子主动分享幼儿园趣事时怎么回应"的话题，但现有 300 条全是"问题行为应对"，没有"主动关系建设"类话题。
遇到这种情况时，执行以下流程：
第一步：在选题清单表格中，将该 day 的 `topicId` 暂时填为 `待补产_场景描述`（如 `待补产_孩子主动分享幼儿园趣事`），继续完成其他 day 的选题，不要停下来等。
第二步：切换到第十三章（F. 话题库扩容）的工作流，按上篇第三章的子场景清单（主动关系建设类 3-6 岁部分）和第五章的写作规范，生产这条新话题。它将获得一个续编的 `_id`，规则见第十三章 13.3 节（如 3-6 岁从 `ph_3_6_101` 开始续编）。
第三步：回到入门计划选题清单，用新话题的实际 `_id` 替换 `待补产_场景描述`，并根据新话题的 `scenario`、`wrongScripts`、`rightScripts` 内容编写该 day 的 `guide` 引导文案。
第四步：导入时，先导入话题库扩容数据（`communication_topics`），再导入训练计划数据（`training_plans`），确保 `topicId` 引用的目标已存在。
第五步：在第十七章的内容校验清单中，逐项检查每个 `topicId` 是否在 `communication_topics` 中确实存在。
这个流程同样适用于主题周（第九章）的选题——主题周更可能出现"理想场景不存在"的情况，因为主题周围绕单一主题展开 7 天，对场景的聚焦要求更高，现有 300 条以"问题行为"为主的分类体系不一定覆盖得到。

## 十、C. 话题关联关系
### 10.1 要生成什么
`topic_relations` 集合文档，每条描述"看完某个话题后推荐哪些相关话题"。用于话题详情页底部"相关话题"区域。首批约 51-63 条。
### 10.2 数据结构
```json
{
  "_id": "rel_ph_7_9_001",
  "topicId": "ph_7_9_001",
  "related": [
    { "topicId": "ph_7_9_003", "type": "same_category", "label": "同场景延伸" },
    { "topicId": "ph_7_9_007", "type": "same_category", "label": "同场景延伸" },
    { "topicId": "ph_7_9_038", "type": "cross_category", "label": "你可能还想看" }
  ]
}
```
关联类型三种：`same_category`（同 level1 + 同 ageGroup 的其他话题）、`cross_category`（不同 level1 但场景有关联）、`theme_chain`（主题周内邻近话题）。
### 10.3 生成策略
只需为入门计划和主题周涉及的约 51-63 条话题手工编排关联关系（2 条同场景延伸 + 1 条跨场景推荐）。非训练计划中的话题靠 `getRelatedTopics` 的 fallback 逻辑兜底（同 level1 + 同 ageGroup 随机取 2 条）。
## 十一、D. guide 引导文案
### 11.1 工作量
入门计划 3×7=21 条 + 主题周首批 7×5-6=约 36 条 = 共约 57 条，每条 30-50 字，总约 2280 字，预估 3-5 小时。
### 11.2 写作模板
入门计划 guide（独立式）：`[1句承接上文] + [1句点出今天的核心问题] + [1句暗示价值]`
主题周 guide（连续式）：`[1句承接昨天的内容] + [1句点出今天的场景和问题] + [1句暗示今天会学到什么]`
### 11.3 示例
入门 Day 1："欢迎开始第一天！每天接孩子放学，问'今天怎么样'，孩子却总是说'不知道'。今天我们就从最高频的场景开始，学会怎么问才能让孩子愿意开口。"
主题周 Day 2："昨天看了催作业的真正原因，今天聚焦一个更隐蔽的问题：孩子明明题会做，却反复说'我不会'。这不是能力问题，而是情绪信号——今天的对话技巧帮你拆解这层伪装。"
### 11.4 质量自检
字数 30-50 字。不复述 scenario。有对话感，不像说明书。主题周 Day 2+ 有承接昨天内容（Day 1 除外）。不用"你应该""你必须"等命令式语态。
## 十二、E. 专题包内容
### 12.1 要生成什么
11 个专题包的章节化图文内容，写入 `communication_packages` 集合。每个包 20-30 章，每章 3 个小节（常见误区/推荐做法/话术示例）。
### 12.2 数据结构
```json
{
  "_id": "emotion",
  "title": "陪孩子一起搞定「情绪火山」",
  "cover": "cloud://xxx/emotion-cover.png",
  "intro": "从识别情绪信号到当场应对，帮你搞定孩子发脾气等8大高频情绪场景",
  ageGroups: ["3-6", "7-9", "10-12"],
  "chapters": [
    {
      "title": "第一章：识别情绪崩溃的信号和阶段",
      "sections": [
        { "heading": "常见误区", "content": "……" },
        { "heading": "推荐做法", "content": "……" },
        { "heading": "话术示例", "content": "……" }
      ]
    }
  ],
  "isFree": false,
  "sortOrder": 1,
  "status": "published"
}
```
### 12.3 生产方式
按上篇第四章的 11 个专题包逐章编写，共 278 章。每章 3 个小节：常见误区（200-400 字）、推荐做法（200-400 字）、话术示例（3-5 组对话，每组含家长说的话 + 简要分析）。
章节需标注所属 `part`（认知篇/场景篇/关系篇/进阶篇/工具篇），核心章节（当场应对、事后复盘类）可写到 1500-2000 字，辅助章节（工具包、误区清单类）保持 500-800 字即可。**不要为凑章节数把一章拆成三章**——用户翻目录看到 30 章很兴奋、点进去发现每章 400 字，落差比 8 章更伤。
首章 `isFree: true`（免费试读），其余锁定。规划 11 个包共 278 章，后续季度扩新包时按同样格式生产。
### 12.4 与 payService 的衔接
新增专题包时 `payService` 会通过 `packageData` 的 `validIds` action 动态获取包 ID 列表，不需要手动扩展数组。新包只需往 `communication_packages.json` 追加文档并导入，`payService` 在 5 分钟缓存过期后自动识别。11 个包 ID 为 emotion、homework、habit、screen、social、money、routine、separation、safety、interest、connection。全部支持单买，`purchaseType` 字段已废除。
### 12.5 质量标准
每章标题不超过 20 字。每小节 200-400 字，用口语化表达，避免学术术语。话术示例中的对话是家长可以直接说出口的话，不是理论描述。整体语气和话题库的 tips 风格一致（见上篇第五章）。
## 十三、F. 话题库扩容
### 13.1 要生成什么
69-90 条新话题，写入 `communication_topics` 集合。字段结构与现有 300 条完全一致。`_id` 在各年龄段现有 100 条之后续编（如 7-9 岁从 `ph_7_9_101` 开始）。
### 13.2 生产方式
按上篇第三章的子场景清单逐条编写。每条包含：1 个场景 + 1 段详细描述 + 3 个错误示范（含分析）+ 3 个正确示范（含分析）+ 1 段专家贴士 + 3 个标签。写作规范见上篇第五章。
建议分批交付，每批 10-15 条，边产出边审核。优先从 7-9 岁开始。
### 13.3 `_id` 续编规则

7-9 岁：现有 `ph_7_9_001` 至 `ph_7_9_100`。新增从 `ph_7_9_101` 开始，上限 `ph_7_9_999`。建议分段：`ph_7_9_101`-`ph_7_9_120` 为"主动沟通与亲子陪伴"类，`ph_7_9_121`-`ph_7_9_130` 为时效性/节日类。
10-12 岁：现有 `ph_10_12_001` 至 `ph_10_12_100`。新增从 `ph_10_12_101` 开始，上限 `ph_10_12_999`。建议分段：`ph_10_12_101`-`ph_10_12_120` 为"深度沟通与信任建立"类，`ph_10_12_121`-`ph_10_12_130` 为时效性/节日类。
注意事项：`_id` 一旦导入并可能在训练计划中被引用，就不可更改（改了会导致训练计划的 `topicId` 悬空）。如果某条话题内容需要修改，直接修改 JSON 文件中该 `_id` 的其他字段后重新导入，upsert 覆盖即可，`_id` 保持不变。如果某条话题需要下线，将 `status` 改为 `"draft"` 而非删除记录。
### 13.4 与训练计划的生产联动
话题库扩容不是完全独立的工作——它的生产需求有两个来源：
来源一：上篇第三章（内容扩容方向）中预设的子场景清单。这是"主动扩容"——你有计划地补充"主动关系建设类"和"时效性/节日类"话题。按 13.3 节的 `_id` 续编规则依次编号即可。
来源二：训练计划（第八章入门计划或第九章主题周）选题时发现的"理想场景不存在"。这是"被动扩容"——你在编训练计划时需要一个特定场景的话题，但现有 300 条里没有。此时按第八章 8.5 节描述的流程，先在话题库扩容中生产这条话题，拿到其 `_id`，再回填到训练计划的 `topicId` 中。
两种来源的生产方式完全一致（都用上篇第五章的写作规范），只是触发时机不同。关键区别在于：来源一可以批量规划、批量生产；来源二是零散的、按需的，每条都对应一个训练计划中明确的使用位置。
实际操作中，建议这样安排：先完成来源一的批量扩容（至少完成首批 7-9 岁的 15 条），再做入门计划和主题周的选题。这样选题时有更大的话题池可选，减少"被动扩容"的次数。如果选题过程中确实需要额外补产，按 8.5 节流程处理即可。

## 十五、导入操作通用步骤
所有内容块的导入流程一致：
1. 把数据写入对应的 `{集合名}.json` 文件（新增集合需同时创建 `.schema.json`）
2. 在微信开发者工具中右键 `cloudfunctions/importData` → "上传并部署：云端安装依赖"
3. 在开发者导入页面（`pages/developer-import`）刷新，自动出现所有可导入的数据集卡片
4. 点击对应集合的"导入"按钮 → 确认弹窗 → 工具自动校验 schema → 创建集合（如不存在）→ 分批写入（每次 20 条）→ 显示进度 → 完成提示
5. 导入完成后在对应页面验证数据是否正常展示
注意事项：
`importData` 使用 `doc(_id).set()` 语义（upsert），相同 `_id` 的记录会被覆盖更新，不会产生重复。重复导入是安全的。
导入操作需要在开发版或体验版中执行，且执行者的 OPENID 需要在 `cloudfunctions/importData/developer-openids.js` 白名单中。

## 十七、内容校验清单
**入门计划/主题周配置**：
- [ ] 每个 `topicId` 在 `communication_topics` 中确实存在
- [ ] `days` 数组长度与计划天数一致（入门=7，主题周=5-6）
- [ ] 每个 day 的 `guide` 字数在 30-50 之间
- [ ] 主题周 Day 2 及以后的 guide 有承接前一天内容
- [ ] `planType` 和 `_id` 前缀匹配（onboarding_/tw_）
- [ ] `ageGroup` 与选题中所有话题的 `ageGroup` 一致
- [ ] `status: "published"`
**话题关联关系**：
- [ ] `topicId` 和所有 `related` 中的 `topicId` 都在 `communication_topics` 中存在
- [ ] `related` 数组不超过 3 条
- [ ] 同一个 `topicId` 不在 `related` 中重复出现
**专题包内容**：
- [ ] `_id` 与 `payService` 的 `VALID_PACKAGE_IDS` 中的 ID 一致
- [ ] `chapters` 数组长度与大纲章节数一致
- [ ] 每章 `sections` 包含至少 2 个小节
- [ ] 首章 `isFree: true`
**话题库扩容**：
- [ ] 每条记录字段结构与 `communication_topics.schema.json` 一致
- [ ] `_id` 不与现有 300 条重复
- [ ] `_id` 符合续编规则（各年龄段从 101 开始，见 13.3 节）
- [ ] `ageGroup` 值为 "3-6"/"7-9"/"10-12" 之一
- [ ] 若该话题是训练计划"被动扩容"产生的，确认其 `_id` 已回填到对应训练计划的 `topicId`
